# Kapiloto V4 Foundation 1A: canonical entities and the Match Ledger

Status: schema and contracts only. Nothing in V1/V2/V3 research, grounding,
derivation, materialization, publication or the UI reads this layer yet.
Migration: `supabase/migrations/20261028010437_kapiloto_v4_entities_match_ledger.sql`.
Contracts: `lib/kapiloto-v4/`. Decision: D-049.

## Why this layer exists

V3 can only reach an expected lineup through a *reported* web XI, and the
Fixture Card carries aggregates (`recentMatches?: Record<string, unknown>[]`,
`coach?: string | null`) rather than per-match lineups, minutes, substitutions
or coaches. Every later V4 component (squad state, lineup and minutes models,
replacement chains, coach model, tactical state, claim resolution, match
engine) needs the same spine: stable identities plus a history of what
happened in each match, kept apart from when Kapiloto learned it.

The layer answers three separate questions:

1. **Who is this?** Canonical players, coaches and existing teams/fixtures.
2. **What did the source say happened?** Immutable Match Ledger observations.
3. **When did Kapiloto first know it?** `first_seen_at`, stamped by the database.

## Canonical identity rules

- The internal UUID is the identity. Provider ids live in
  `provider_player_mappings` / `provider_coach_mappings` (primary key
  `(provider, provider_id)`), using the same `mapping_status` values as teams.
  Only `confirmed` and `manual_override` resolve automatically.
- `unique (provider, player_id)`: two provider ids can never silently collapse
  into one canonical player. A provider-side duplicate becomes a second
  canonical player plus an explicit merge.
- Aliases are unique **per entity**, not globally. Two different players may
  both be "Yossi Cohen"; an alias lookup that returns several surviving
  entities is ambiguous (`resolveAliasCandidates`) and must never pick one.
- `normalized_alias` is generated by `private.normalize_entity_alias`
  (mirrored by `normalizeEntityAlias`): Hebrew points removed, geresh/gershayim,
  maqaf, typographic quotes/dashes and NBSP unified, whitespace collapsed,
  lower-cased. Transliteration variants are deliberately not unified.
- **When in doubt, create a new canonical entity.** A wrong split is repaired
  by a merge (`identity_status = 'merged'`, `merged_into_*_id`, one hop,
  trigger-enforced, ledger rows untouched). A wrong merge is reversible
  because nothing is rewritten, but every model read made while it stood used
  the merged history.
- No fuzzy resolution exists yet. Ingestion resolves provider ids through
  confirmed mappings and creates a new canonical entity otherwise.

## Canonical identity after merges

Decision D-050 (`kapiloto-canonical-identity-v1`). A merge (A → B) is a
data-quality correction, not a football claim:

- **Raw ledger rows are immutable.** Rows written under A keep `player_id = A`
  (or `coach_id = A`), with their raw provider ids and names.
- **Model-facing reads use the current survivor, at every cutoff.**
  `match_ledger_provider_player_matches_as_of(provider, B, ...)` returns B's
  matches plus every match stored under an id merged into B. Asking with A
  **redirects** to B's history: any member of an identity class addresses the
  whole class, and each row reports `canonical_player_id` (B) next to
  `observed_player_id` (what the version stored). Team history returns
  `observed_coach_id` and `canonical_coach_id`; coach models group by the
  canonical id. `team_coach_tenures_as_of` stays a raw assertion history
  (`coach_id` as asserted) plus `canonical_coach_id`.
- **Information time still governs football facts.** A merge done today makes
  A's Oct 1 match part of B's history at an Oct 5 cutoff, but only for versions
  whose `first_seen_at` is before Oct 5.
- **Undo is exact.** Because no row is rewritten, un-merging A restores the
  previous reads.
- **No double counting.** The merge guard keeps at most one member of an
  identity class per observation version (below), and the reads return one
  version per fixture, so each fixture appears once.

### Writes accept surviving ids only

Ingestion **rejects** merged ids; it never canonicalizes them. The RPC checks
every position (`players.player_id`, `substitutions.player_off_id` /
`player_on_id`, `events.player_id`, `events.related_player_id`,
`teams.coach_id`, `events.coach_id`) after the fixture locks and **before**
the hash comparison, so a payload resolved with a stale id is an error, never
an `unchanged` no-op. The child triggers repeat the check for direct inserts
(the substitution and event player positions reference the squad rows, so the
squad check covers them). Tenure writes follow the same rule; a later version
of a tenure asserted for A names A's survivor.

Rejecting instead of canonicalizing keeps one boundary: the payload, the
stored ids and `content_sha256` are always the same ids, so no post-hash
normalization can create spurious versions, and a payload that lists A and B
as two people fails loudly instead of colliding. The cost: the first re-ingest
of a fixture after a merge writes one new version whose football content is
unchanged and whose canonical ids are now survivors. The reads treat both
versions identically.

### Co-occurrence guard

A merge is refused when the two identities appear as two people in one stored
observation version, checked against the target's whole identity class:

- players: both in one version's matchday squad;
- coaches: linked to **opposite** teams of one version (head coach of one side
  and head coach or a staff card of the other). Same-side appearances (a head
  coach and a staff card of the same team) are not refused.

Superseded and withdrawn versions count, because as-of reads at earlier
cutoffs still return them. A corrected version therefore does **not** unblock
the merge (this deliberately departs from "correct first, then merge"). If a
provider really listed one person twice, the two canonical entities stay
separate until a reviewed quarantine mechanism for corrupt versions exists.

### Aliases and provider mappings

- `player_alias_candidates(alias)` / `coach_alias_candidates(alias)` return
  each matching entity with its survivor. `resolveAliasCandidates` compares
  survivors: `[A, B]` with A → B resolves to B; candidates with two different
  survivors stay ambiguous. Aliases of merged rows are kept.
- A mapping that predates a merge may keep pointing at A; its metadata and
  status stay editable. New or re-pointed mappings must target a survivor.
  `resolve_provider_player_ids` / `resolve_provider_coach_ids` return
  authoritative mappings resolved to the survivor (P → A → B gives B).
- Ingestion mapping checks are merge-aware in both directions.

### Identity time

Canonical identity is read at its current state, not as of the cutoff:

- Exact historical model inputs are preserved by the Foundation 1B prediction
  registry, which snapshots the resolved inputs a prediction used. The
  identity graph itself is not versioned in 1A, so it cannot be replayed.
- Backtests can be slightly optimistic: a duplicate tends to be noticed after
  a player becomes prominent, and a backtest sees the merged history a live
  run at that time did not. The registry makes the live/backtest gap
  measurable.
- **Mis-attribution is not a merge.** When a provider id was attributed to
  the wrong person C (C is a real person with other matches), the fix is to
  re-point the mapping. Rows already stored under C are reconciled by a
  corrected observation version, which is visible only from its
  `first_seen_at`, so mis-attribution corrections are **not** retroactive in
  1A. If C exists only because of the mistake, it is a duplicate: merge it,
  and the correction is retroactive. Retroactive mis-attribution repair would
  need a read-time identity overlay keyed by `(provider, provider_player_id)`
  with its own co-occurrence guard; that belongs to the ingestion /
  reconciliation task.

## Time: event time vs information time

| Column | Meaning | Who writes it | Used for as-of? |
| --- | --- | --- | --- |
| `kickoff_at`, `minute`, `stoppage_minute`, `starts_on_*`, `ends_on_*` | Event time: what the source says happened and when | Ingester | Only as a secondary filter |
| `retrieved_at` | When the ingester fetched the source | Ingester | **Never** |
| `source_updated_at` | Provider's own last-updated stamp, if supplied | Ingester | Never |
| `first_seen_at` | Information time: when Kapiloto first stored this version | **Database** (`private.kapiloto_information_clock()`) | **Always** |
| `ingest_statement_at` | Sealing key: `statement_timestamp()` of the statement that wrote the header | Database | **Never** |
| `contract_version`, `source_version`, `ingest_version`, `definition_version` | Payload contract / provider API / ingest code / stat definition versions | RPC / ingester | — |

`first_seen_at` plays the role of the trigger-stamped `captured_at` in the
shadow-evaluation tables. The ledger names it `first_seen_at` because
re-ingesting identical content does not create a new row: the stored time is
the first time this content was seen.

**Which clock.** `private.kapiloto_information_clock()` returns
`clock_timestamp()`, evaluated once when the header row is inserted (after the
fixture locks are held); every child copies the header's value, so one
observation has one information time.

- `now()` was rejected: it is the transaction start, so a transaction opened
  early would backdate knowledge written later.
- `statement_timestamp()` was rejected as the information clock: it is the
  receipt time of the client command, so time spent waiting for a competing
  writer's lock would be backdated, and two serialized versions of one fixture
  could get inverted times. It is used only as the sealing key.

The residual gap is commit latency: a row becomes visible at commit, shortly
after `first_seen_at`. The payload was already in Kapiloto's hands at
`first_seen_at`, so this does not admit future information; a replay at a
cutoff inside that window can see a row a live reader could not yet see.

## Bitemporal and as-of rules

**Rule (`kapiloto-as-of-first-seen-v1`).** To reconstruct what Kapiloto knew
at cutoff T:

1. keep versions with `first_seen_at <= T`;
2. per `(fixture, provider)` take the highest surviving `observation_version`;
3. only then apply event-time filters (`kickoff_at < T`, `match_status = 'finished'`).

Event time never admits a row. Filtering on event time before step 2 would
also be wrong, because it could resurrect a version that a visible newer
version had corrected.

**The leakage example.** A match is played on Oct 30. The provider backfills
it (or adds an injury record dated Oct 30) and Kapiloto first stores it on
Nov 3. A reconstruction at Nov 1 calls
`match_ledger_provider_team_matches_as_of('sportmonks', team, '2026-11-01')`: the Nov 3 version fails
step 1, so the match is absent, even though its `kickoff_at` is before Nov 1.
`lib/kapiloto-v4/as-of-leakage.test.ts` asserts this for team history,
fixture lookup and player history.

**Why it holds by construction:**

- `first_seen_at` is overwritten on insert by the database clock. A writer
  cannot backdate it, and service_role cannot redefine the clock (owner only).
- Observations and children are immutable (update/delete/truncate raise).
- Children are **sealed to the writing statement**
  (`header.ingest_statement_at = statement_timestamp()`): not even a later
  statement in the same transaction can append to a header and inherit its
  earlier information time. Ingestion is therefore one RPC statement.
- A correction is a new version (`observation_version + 1`, assigned by
  trigger under the fixture lock); identical content is a no-op, and
  `first_seen_at` never decreases within one fixture/provider history.
- `retrieved_at` may not exceed `first_seen_at` (+5 minutes clock skew), and a
  `finished` version cannot be first seen before `kickoff_at + 105 minutes`.
- `match_ledger_team_records` and `match_ledger_players` carry trigger-copied
  `kickoff_at` and `first_seen_at`, indexed for team-history and
  player-history as-of scans.

**What it does not do.** Code that queries the tables directly must apply the
same rule (including "a latest withdrawal hides the pair"); use the as-of
functions or `latestProviderObservationsAsOf`. Backfilled
history gets `first_seen_at` = backfill time, so a strict reconstruction at a
cutoff before the backfill sees nothing. Training models on backfilled
history needs an explicit, versioned "assumed availability" policy (for
example "a finished match's lineup and events were public at kickoff + 3h";
never applied to injury/sidelined records). That policy is a later decision;
`capture_mode` (`scheduled_sync`/`backfill`/`manual_import`) is recorded now
so it can be applied.

## Concurrency

Every write that versions or claims an identity takes a transaction-scoped
advisory lock (held until commit) and refuses to run outside READ COMMITTED,
because lock-then-check is only sound when each check sees writers that
committed first.

| Invariant | Lock |
| --- | --- |
| A provider fixture id is actively attached to at most one canonical fixture | `(provider, provider_fixture_id)`, taken first by the RPC and by the header trigger (direct inserts included) |
| Observation versions are contiguous, deduplicated and time-monotonic | `(fixture, provider)`, taken second |
| Merges never form cycles or chains; a merge never makes one version list one person twice | `kapiloto_identity:players` / `kapiloto_identity:coaches` exclusive, taken when `identity_status` / `merged_into_*` changes |
| Provider player/coach mappings and the ledger rows that check them | the same identity lock: exclusive for mapping writes, shared for ledger squad, team-record, staff-card and tenure writes |
| Tenure versions are deterministic | `tenure_key` |

Lock order is fixed: provider-fixture, then fixture/provider (or `tenure_key`),
then the identity locks. Shared identity locks never block each other, so
ledger writers only wait for a merge or a mapping write in flight.

The provider-fixture check considers a fixture's latest version carrying the
id: after a **withdrawal**, the id may be recorded for the correct fixture, and
the original fixture may be re-recorded under its correct id.

### Cross-table consistency (mappings vs ledger)

| Race | Status |
| --- | --- |
| Confirmed player mapping vs ledger player ingest | **Serialized.** Mapping writes take `kapiloto_identity:players` exclusively; ledger squad rows check mappings under it shared. A ledger row never contradicts an authoritative mapping that committed before it. |
| Coach mapping vs ledger team record / staff card | **Serialized** the same way (`kapiloto_identity:coaches`). |
| Merge vs ledger ingest | **Serialized** by the same locks: merged-id rejection and the co-occurrence guard see each other's committed writes. |
| `provider_fixture_mappings` (V3) vs ledger fixture ingest | **Not serialized (deferred).** V3 writes that table (for example the live-settlement RPC) without the ledger's provider-fixture lock. Adding a trigger or lock there would change V3 runtime behavior, so the ledger's mapping check is point-in-time only. |
| Correcting an authoritative mapping after ledger versions exist | **Allowed by design**; the ledger is not rewritten. |

Mappings are corrected after the fact by design, so "the ledger agrees with
the current mappings" can never be an invariant. The ledger stores raw
provider ids, so drift is detectable: `match_ledger_mapping_conflicts(provider)`
lists current (latest, non-withdrawn) versions whose stored canonical fixture,
player or coach disagrees with the current authoritative mapping of the raw
id. The repair is a corrected version or a withdrawal. Withdrawals skip the
attachment checks, so they stay possible after V3 moved a fixture mapping.

**Hard requirement for the ingestion task:** one writer must resolve or create
the `provider_fixture_mappings` row and record the ledger observation in the
same READ COMMITTED transaction, holding `lock_match_ledger_fixture` before it
reads or writes the mapping. Any other writer that can re-point a fixture
mapping must take the same lock or be followed by a reconciliation pass over
`match_ledger_mapping_conflicts`.

## Multi-provider contract

History reads are **provider-scoped by signature**:
`match_ledger_provider_team_matches_as_of(provider, team, cutoff, limit)` and
`match_ledger_provider_player_matches_as_of(provider, player, cutoff, limit)`
require a provider and return at most one row per canonical fixture, so a
last-N window can never count one match twice. A null provider is an error,
not a union. There is deliberately no all-providers history: combining
providers needs an explicit precedence/fusion policy and will be a separate,
named canonical-match API. Model code must never merge two provider-scoped
results into one last-N list.

## Immutable observation principle

- **Football corrections** (score, card, minute, lineup changes) are new
  observation versions. Old versions remain readable forever.
- **Withdrawals** retract a provider's data for a fixture (attached to the
  wrong fixture, removed by the provider): a header-only version with
  `observation_kind = 'withdrawal'` and a reason. Cutoffs after it see nothing
  from that provider for the fixture; earlier cutoffs still see the earlier
  versions. A later real observation becomes the next version.
- **Identity corrections** (duplicate player) are merges on the mutable
  canonical tables. Ledger rows keep the id they were written with, and
  readers follow the one-hop redirect.
- **Derived data** (game-state segments, later formation families) lives in
  separate tables keyed by observation and `derivation_version`. It carries no
  information beyond its observation, so it is not sealed.
- Formation families are **not** stored in provider observations. Only the
  provider's `formation_nominal` is.

## Match Ledger semantics

- One observation = one provider's complete view of one fixture at one
  retrieval. It always has exactly two team records (home/away, checked
  against `fixtures` orientation; the opponent is filled by trigger).
- Database-enforced completeness (deferred constraint triggers that the RPC
  forces before returning; any other writer meets them at commit): a finished
  version has a 90-minute score; `lineup_status = 'complete'` means exactly 11
  starters; `not_provided` forbids rows of that family for that team.
  `complete` is a claim of full representation, not a minimum: zero
  substitutions or cards is valid.
- Completeness is explicit per team and data family
  (`complete`/`partial`/`not_provided`), so a results-only source (a cup or a
  Liga Leumit match from an IFA sheet) and a full Sportmonks payload use the
  same tables. `provider` is any lowercase key (`sportmonks`, `api_football`,
  `ifa`, ...); no provider-specific columns exist.
- Players: at most 11 starters per team (trigger), unique formation slots and
  shirt numbers, starters cannot be "not appeared". Substitutions must
  reference squad members of the same team, and a starter cannot come on.
  Event players must belong to the acting team's squad; `related_player_id`
  (assist, penalty goalkeeper) must be in the observation's squad, either team,
  and only on goal/penalty events.
- Mapping consistency: a supplied `provider_player_id` / `provider_coach_id`
  must not contradict a `confirmed`/`manual_override` mapping in either
  direction (merge-aware). No provider id, or only an `unverified` mapping,
  is unknown rather than contradictory and is accepted.
- Event `team_id` is the acting player's/coach's team. For an own goal that is
  the conceding team (`scoringTeamId()` returns the benefiting team).
  Staff cards carry `coach_id` plus `staff_role`
  (`head_coach`/`assistant_coach`/`other_staff`/`unknown`). The database
  refuses the opponent's head coach, a `head_coach` card naming someone other
  than the team's known head coach, and an assistant/staff card naming the
  team's own head coach. An unknown team head coach constrains nothing.
- Team stats must use a stat definition of the observation's own provider.
- Minutes use `minute` + `stoppage_minute` (45+2 → 45, 2), optional `second`
  and `period`.
- Stats: `stat_key` names the meaning (`possession_pct`, `shots_on_target`,
  `expected_goals`, ...); the provider type and `definition_version` keep raw
  identity. A changed provider definition (the Aug 2024 Sportmonks type-set
  drift) is a new definition row, never an update. Values are finite numerics.
- Segments: one row per segment from a team's perspective, split at goals, red
  cards and period boundaries; `score_diff` and `men_diff` are generated.

### Ingestion contract

`match_ledger_record_observation` accepts `kapiloto-match-ledger-observation-v1`
JSON (built by `buildMatchLedgerObservationPayload`, checked first by
`validateMatchLedgerObservation`). It rejects unknown keys, canonicalizes
types and order, hashes the football content (retrieval metadata excluded),
returns `unchanged` when the latest version has the same hash, and otherwise
writes the header and all children in one transaction. A provider fixture id
that `provider_fixture_mappings` maps to a different fixture, or that is
already recorded for a different canonical fixture (a duplicated fixture),
is refused, as are repeated provider event ids within one version, merged
canonical ids in any position, and one coach leading both teams.
`buildMatchLedgerWithdrawalPayload` builds the withdrawal form.

## How later V4 components consume this layer

| Component | Reads |
| --- | --- |
| Squad state | `match_ledger_provider_player_matches_as_of`: starts, minutes, last start, positions from one version per fixture, merged duplicates included; later joined with availability observations |
| Lineup model (P(start)) | Last N team records + squads as of cutoff; coach from `canonical_coach_id`; formation slots |
| Minutes model | `minutes_played`, `entered_minute`, `exited_minute`, substitution minutes and reasons |
| Replacement chains | Consecutive matches: who held a `formation_position` when the usual player was absent |
| Coach model | Team records grouped by `canonical_coach_id` across clubs; `team_coach_tenures_as_of` (`canonical_coach_id`) for regimes and dates |
| Tactical state | Team stats by `stat_key` and definition version, opponent rows from the same observation, segments for game-state context |
| Claim resolution | Ledger truth (actual XI, minutes, cards) resolves journalist lineup/injury claims made before kickoff |
| Match engine | Goal and card minutes, segments, men difference |

All of them must read through the as-of rule. None may read `fixtures`'
mutable score/status/kickoff for historical reconstruction.

## Example: Hapoel Tel Aviv vs Maccabi Haifa (illustrative only)

No data is inserted by this task. Names other than the clubs are placeholders.

To reconstruct Hapoel's last matches before a research cutoff of
2026-10-31T12:00Z for the 2026-11-02 fixture:

```
match_ledger_provider_team_matches_as_of('sportmonks', <hapoel>, '2026-10-31T12:00Z', 5)
match_ledger_provider_team_matches_as_of('ifa', <hapoel>, '2026-10-31T12:00Z', 5)
```

| Kickoff (event time) | Provider | Version | first_seen_at | Side | Opp. | Score | Coach | Formation | Lineup |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Oct 29 (Toto Cup final) | `ifa` | 1 | Oct 30 08:00 | home (neutral venue) | X | 1–1 (aet/pens on header) | `<coach H>` | — | partial |
| Oct 25 | `sportmonks` | 2 | Oct 27 06:00 | home | Y | 2–0 | `<coach H>` | 4-2-3-1 | complete |
| Oct 18 | `sportmonks` | 1 | Oct 19 06:00 | away | Z | 1–1 | `<coach H>` | 4-2-3-1 | complete |

- The Oct 25 match shows version 2 because a provider correction (for
  example a reassigned goal) was first seen on Oct 27, before the cutoff. A
  correction first seen on Nov 3 would not appear; version 2 would still be
  returned.
- The cup final comes from the IFA sheet with `lineup_status = 'partial'` and
  `statistics_status = 'not_provided'`, because Sportmonks does not cover
  Israeli cups. It still contributes minutes (fatigue) for the players listed.
- Each row's `observation_id` leads to `match_ledger_players` (11 starters
  with `formation_position`, bench, minutes), substitutions, events (for
  example a red card for `<player S>` in the previous match, which a later
  suspension rule reads) and team stats.
- Haifa is reconstructed the same way. Anything a provider adds after the
  cutoff (a backfilled match, a corrected card, a sidelined record dated
  before the cutoff) is invisible to this run and to any later replay of it.

## Security

All 15 tables are in `public` with RLS enabled, no policies, and
`revoke all ... from public, anon, authenticated`. The ten public functions are
security-invoker, revoked from `public, anon, authenticated` and granted to
`service_role` only. The private helpers that triggers, generated columns and
the RPC call by name (`kapiloto_information_clock`, `normalize_entity_alias`,
`match_ledger_assert_keys`, `match_ledger_record_withdrawal`,
`kapiloto_require_read_committed`, `surviving_player_id`, `surviving_coach_id`,
`lock_match_ledger_fixture`, `lock_canonical_identity`,
`match_ledger_assert_surviving_ids`) are executable by `service_role` only, which
also receives `usage` on schema `private` (not exposed by the Data API). No
`security definer` function is added. `lib/kapiloto-v4/security.test.ts`
replays Supabase's default grants and verifies the revokes and the
service_role ingestion path.

## Not in Foundation 1A

Lineup/formation/starter probabilities, availability, player impact, match
engine, tactical state model, research planner, claim resolution, Sol prompt
or UI changes, ingestion jobs, Sportmonks backfill, IFA scraper, raw document
archive (`raw_observation_id` is reserved for it), and wiring into
`fixture-card.ts`.

Foundation 1B (D-051, `KAPILOTO-V4-KNOWLEDGE-REGISTRY.md`) adds the document
archive, claims, claim resolutions and the prediction registry. A provider
response can be archived as a `provider_response` document version. Linking
`raw_observation_id` to it is left to the ingestion task (the column has no
foreign key).
